# PharmaDesk — Production Hardening Plan
_Generated from a 67-agent (55 audit + 11 synthesis + 1 critique) production-readiness review comparing the Qt6/C++ port against the PHP source-of-truth (`../pos`)._

**Findings:** 409 total — high: 74, medium: 153, low: 170, info: 10, critical: 2. Audited 55/55 areas.

**By category:** build_release 8, correctness 68, docs_process 13, maintainability 26, performance 11, port_parity 84, reliability 73, security 32, testing 60, ux 34

## Critique — production-readiness verdict

> NOT production-ready: the per-module port is genuinely strong on money/stock/FEFO math, but cross-cutting medical-retail essentials — data migration/cutover, crash/power-loss durability with tested restore, fail-safe and tamper-evident audit, injected-failure and end-to-end acceptance tests, a release-gating CI, externally-grounded regulatory compliance, and verified launch on the actual Wayland AlmaLinux target — are missing or unproven, and these are blockers for a system that dispenses drugs and handles cash.

### Top risks
- Data-loss / inconsistency on crash or power loss: synchronous=NORMAL, no busy_timeout, no integrity_check, no tested restore, and ZERO injected-mid-transaction-failure tests mean the core never-leave-stock-inconsistent guarantee is unproven exactly where it matters most — an unattended single PC.
- No data migration from the live PHP/Postgres system: only the 318-row catalog seeds. Going live would discard all existing stock, sales history, audit chain, and controlled-drug register continuity. A hard blocker absent from every plan theme.
- Audit trail is neither tamper-evident (HMAC chain empty/unimplemented) nor fail-safe (26 write sites ignore failure), so a regulator-facing controlled-substance/narcotic register can be silently altered or silently fail to record — a compliance and legal exposure for a drug-dispensing system.
- Compliance is defined only as match-the-PHP-app with no external regulatory requirement cited (controlled-drug register, retention period, tax receipt, patient-PII privacy); faithfully reproducing an unvalidated spec may faithfully reproduce non-compliance.
- No release gate: no CI, no CTest registration, no packaged-binary smoke test, and a money-parity test that itself uses floating point — a red or broken build can ship and the strongest safety claim (bit-for-bit money) has a hole in its own verifier.
- Target-platform launch unverified: AlmaLinux 10 defaults to Wayland but the AppImage bundles no Wayland platform plugin and there is no evidence it starts on a clean target box.

### Gaps not covered by any plan theme
- DATA MIGRATION FROM THE LIVE PHP/POSTGRES SYSTEM IS COMPLETELY ABSENT. The catalog importer (medicines_export.csv, 318 rows) seeds only the medicine catalog. There is no examined path to migrate existing batches/stock-on-hand, open sessions, historical sales, inventory_movements, audit_log, GRNs, returns, or supplier records from the production Postgres app to SQLite. A pharmacy cannot go live with zero stock and zero sales history. Cutover/parallel-run strategy, opening-balance reconciliation, and migrated-audit-chain continuity are unaddressed across all 12 plan themes.
- NO END-TO-END / SYSTEM-LEVEL ACCEPTANCE TEST exists. Every test is a unit or single-service DB-integration test. Nothing drives a full day (open shift -> GRN -> POS sales cash+card+controlled -> return/adjudicate -> void -> close -> Z-report -> reconcile) and asserts the books balance and the audit chain is continuous. The never-leave-stock-inconsistent guarantee is only asserted per-service, never across the whole workflow.
- INJECTED MID-TRANSACTION FAILURE TESTS ARE MISSING despite CLAUDE.md explicitly requiring them. Reliability tests cover business-rule REJECTIONS only; no test forces a fault (disk-full, killed process, SQLITE_BUSY, failed audit insert) partway through a sale/return/GRN and proves stock+ledger+money are consistent on recovery. The most load-bearing pharmacy-safety claim is unproven.
- POWER-LOSS / CRASH DURABILITY ON A SINGLE PC IS UNVERIFIED. PRAGMA synchronous left at WAL-default NORMAL means the last committed sale can be lost on power loss; no busy_timeout (confirmed absent), no integrity_check on startup or before destructive ALTER-TABLE migrations. For an unattended retail counter on AlmaLinux this is the most likely real-world data-loss vector and it is only noted, never tested or decided (no documented UPS assumption).
- AUDIT TAMPER-EVIDENCE IS GONE, NOT JUST SIMPLIFIED. The HMAC chain (prev_hmac/row_hmac) is entirely unimplemented (confirmed: only a deferral comment in Audit.h, columns always empty) and there is no offline verifier. A regulator-facing medical audit log that is merely UPDATE/DELETE-trigger-blocked is not tamper-evident against anyone with file/SQLite access. The plan lists HMAC as a workstream but never decides whether shipping with empty chain columns is acceptable, and no external retention/compliance requirement is cited to justify it.
- 26 Audit::write CALL SITES IGNORE THE RETURN VALUE (confirmed), so a failed audit insert silently lets the business transaction commit. Flagged as scattered findings rather than one enforced invariant; there is no single throwing choke point guaranteeing audit-failure aborts every money/stock mutation. The append-only audit guarantee is defeatable by any audit-write error.
- REGULATORY/COMPLIANCE REQUIREMENTS ARE NEVER STATED. No summary or plan item cites the actual legal regime (DRAP/Pakistan controlled-drug register format, narcotic record retention period, FBR tax-receipt requirements, data-retention duration, patient-PII privacy). Compliance is treated as match-the-PHP-app; the PHP app's own compliance is assumed, never validated against an external standard. Faithful reproduction may faithfully reproduce non-compliance.
- BACKUP RESTORE IS UNIMPLEMENTED AND UNTESTED (confirmed: no restore code in src). The plan calls for a rehearsed recovery runbook but there is nothing to rehearse; plus no -wal/-shm sidecar handling, no retention/pruning, world-readable backup files exposing bcrypt PINs and patient records, and an unchecked WAL-checkpoint result. A single-PC system with no tested restore is one disk failure from total loss.
- WAYLAND COMPATIBILITY ON THE ACTUAL TARGET IS UNVERIFIED. AlmaLinux 10 GNOME defaults to Wayland, but the AppImage bundles only libqxcb + libqoffscreen (confirmed; no Wayland platform plugin). Listed P2 but never tested on the real target. No examined evidence the AppImage even launches on a clean AlmaLinux 10 box.
- NO RELEASE-GATING CI EXISTS (confirmed: no .github, no CTest/add_test in CMakeLists, no runner script). All-tests-pass is unenforced; a red build can ship. No automated post-build smoke test of the packaged binary either. The strong unit suite gives false confidence because nothing prevents regressions or a broken AppImage from being released.
- CONCURRENCY / SECOND-CONNECTION SAFETY IS ASSUMED AWAY EVERYWHERE. Receipt-, grn-, and adjustment-number minting use read-then-insert with the PHP advisory locks dropped and no busy_timeout. Every summary excuses this with single-PC/single-connection, but auto-backup, an external WAL reader, a future second window, or a restore tool each introduce a second connection. The single-connection assumption is never enforced or documented as a hard constraint, leaving latent TOCTOU windows.
- FLOATING-POINT IN A MONEY TEST ASSERTION violates the no-float rule (CAST AS REAL / toDouble / 0.005 epsilon) and can mask sub-cent rounding bugs in the exact path CLAUDE.md says must match PHP bit-for-bit. Until fixed, the money-parity guarantee has a hole in its own verification harness.
- NO TRUE PHP-ORACLE PARITY HARNESS. Money/FEFO/cost/tax/SaleCalculator are checked against hand-transcribed golden constants, not live PHP output, and composed cross-class flows (SaleCalculator+CostBlender+report aggregation) are never compared end-to-end to the PHP app on shared fixtures. Reports explicitly never assert exact PKR amounts. Bit-for-bit is claimed but not mechanically guaranteed for composed flows.
- MONEY int64 OVERFLOW IS UNGUARDED AND UNTESTED. PHP bcmath is arbitrary-precision; the C++ Money silently overflows in fromString/mul with no guard or boundary test. Low probability at pharmacy scale, but a silent wrong total is the worst failure class for a money system.
- OPERATIONAL OWNERSHIP / UPDATE DELIVERY UNADDRESSED. No examined plan for who installs updates on the single AlmaLinux box, how a patched AppImage is delivered/verified on-site, how schema migrates forward in-field, or how a failed in-field migration rolls back. Migration runner has no pre-migration backup/integrity_check and no rollback test.
- VALIDATION-AT-IMPORT AND BAD-DATA RESILIENCE under-examined: CatalogImporter never validates enum fields (form/schedule/tax) and silently drops ragged rows; CostBlender returns silent 0.0000 on degenerate input (units_per_purchase=0) instead of throwing like PHP, with no schema CHECK. A future re-import of a different export could silently post zero-cost batches.
- PATIENT-DATA / PII HANDLING DROPPED OR UNEXAMINED: parked carts drop customer name/phone/CNIC that PHP persists; backups are world-readable; no examined data-at-rest encryption decision for a DB holding patient identifiers and controlled-drug dispensing records. Medical-record privacy obligations are never assessed.

## CRITICAL findings

### [ui_inventory] Stock adjustments skip the mandatory manager-PIN re-confirmation that PHP enforces
- **File:** `src/ui/AdjustmentsPage.cpp:281-319`
- PHP adjustments.php gates every adjustment behind ManagerOverride::verify($pin, 'stock_adjustment') and throws if the PIN is missing/invalid, with an explicit comment that this 'protects against unattended workstations being used to write off stock'. The Qt AdjustmentsPage::applyAdjustment() calls StockAdjuster::adjust(...) directly with no PIN prompt at all — anyone sitting at an unlocked manager session (or any non-cashier who can reach the Inventory tab) can write off arbitrary quantities/value of stock with zero re-auth. The building block exists: ManagerOverrideDialog + UserRepository::verifyManagerOverride are already used by PosTerminalPage and ReturnsPage, so this is a missing wiring, not missing infrastructure. This is a direct security-control regression versus the source-of-truth spec on a money/stock path.
- **Fix:** Before calling StockAdjuster::adjust, present ManagerOverrideDialog and verify via UserRepository::verifyManagerOverride(pin, m_userId, "stock_adjustment") (allowing self-confirm, matching PHP), aborting the adjustment if it fails. Cover with a test that an adjustment without a valid PIN is rejected. _(effort M)_

### [ui_returns] Cashier can process a full refund with no manager authorization (segregation-of-duties bypass)
- **File:** `src/ui/ReturnsPage.cpp:504-579`
- processReturn() only prompts for credentials when ControlledSubstancePolicy::requiresWitness(schedule) is true (NARCOTIC only). For every ordinary medicine, a logged-in CASHIER refunds cash and disposes of stock (RESTOCK or WRITE_OFF) in a single click with zero second-person check. The PHP source (pos/frontend/pages/pos/returns/initiate.php) requires, for a non-manager operator, a ManagerOverride::verify(...,'return_initiate') PIN belonging to a DIFFERENT user before Returns::initiate is ever called — explicit segregation of duties on a cash-out / stock-mutating path. The Qt port drops this entirely. ReturnService::commitReturn sets authorized_by = m_userId (the cashier themself), so the audit row also records no independent authorizer.
- **Fix:** Before calling commitReturn for a non-manager user, gate the refund behind a ManagerOverrideDialog and UserRepository::verifyManagerOverride with a 'return_initiate' purpose, requiring a manager/admin whose id != m_userId; pass that id through as the authorizing manager (separate from the narcotic witness). Mirror the PHP rule that MANAGER/ADMIN operators self-authorize. _(effort M)_

## Plan (by theme)

### Build & Release Engineering: test gating, supply-chain integrity, and reproducible/traceable packaging

PharmaDesk is a medical-retail money/stock/expiry system, yet its release chain has no enforcement layer: the 1000+-assertion suite exists but `ctest` runs zero tests (no enable_testing()/add_test()), there is no CI or runner script, and nothing gates a red FEFO/Money regression from being packaged. The packaging script fetches all build tooling (linuxdeploy, the Qt plugin, appimagetool, the type-2 runtime) from moving ":continuous" tags with `curl | chmod +x` and no checksum — the single weakest link in the release chain and a direct supply-chain risk for a system holding controlled-substance records. Provenance is further undermined by a hardcoded 0.1.0 version with no VCS linkage (the project isn't even a git repo), non-reproducible builds (no SOURCE_DATE_EPOCH, embedded build-host paths, fresh-rebuilt ICU), and no published release hash. Secondary quality gaps — no sanitizer/static-analysis path for the hand-rolled decimal/FEFO math, dev builds with no defined CMAKE_BUILD_TYPE (so test codegen differs from the shipped Release binary), Wayland plugin omission on a Wayland-default target, and an unvalidated .desktop entry — round out the work. I sequence enforcement first (P0: tests must gate, tooling must be pinned+verified), then provenance/correctness-confidence (P1), then quality and polish (P2/P3). I confirmed against the source: run_all.cpp already returns exit 0 only when every assertion passes (so CTest wiring is a few lines), CMakeLists.txt has no enable_testing(), build-appimage.sh fetches from /continuous/ with no SHA, and `.git` is absent.

#### `P0` Gate every release on a green test suite (CTest + runner + CI)
- In CMakeLists.txt (after line 183), add enable_testing() and register the existing executables: add_test(NAME suite COMMAND pharmadesk_tests) and add_test(NAME barcode COMMAND pharmadesk_barcode_test); these already return non-zero on failure (run_all.cpp: 'Exit code 0 only if every assertion passed'), so CTest will fail correctly with no test rewrites.
- Set the test working directory/env so the suite's isolated test-mode SQLite DB and offscreen platform work headlessly: set_tests_properties(suite PROPERTIES ENVIRONMENT "QT_QPA_PLATFORM=offscreen") and a TIMEOUT (e.g. 300s).
- Optionally also register pharmadesk_smoke as a test so the headless boot path is exercised by ctest, not just manual runs.
- Add tests/run.sh (mirroring the PHP tests/run.php convention noted in the finding): configure with -DBUILD_TESTING=ON -DCMAKE_BUILD_TYPE=RelWithDebInfo, build, then `ctest --output-on-failure --test-dir <build>`; exit non-zero on any failure. Make it the single command both humans and CI call.
- Add a minimal CI job (GitHub Actions .github/workflows/ci.yml or GitLab .gitlab-ci.yml) on a Qt6 container that runs tests/run.sh on every push/PR; for the air-gapped/single-PC reality, at minimum commit the runner script and a pre-commit/pre-push git hook that calls it so a red suite cannot be committed.
- Make build-appimage.sh refuse to package a red tree: before the existing 'tests off' Release configure (around line 56), run a separate BUILD_TESTING=ON configure+build+ctest step and abort (set -e already on) if ctest fails — so the AppImage is never cut from failing code.
- **✓ Acceptance:** `ctest --test-dir <build> --output-on-failure` discovers and runs pharmadesk_tests (and barcode), reports the full assertion count, and returns non-zero if any assertion fails. tests/run.sh exists, is executable, and is green on a clean tree. CI (or the git hook) blocks merging/committing a deliberately-broken FEFO or Money change. build-appimage.sh aborts before packaging when the suite is red.

#### `P0` Harden the release supply chain: pin and verify all build tooling
- In build-appimage.sh, replace the '/continuous/' base URLs (lines ~30-35 and the type-2 runtime at ~180-181) with specific tagged releases for linuxdeploy, linuxdeploy-plugin-qt, appimagetool, and type2-runtime; record the chosen versions in the script header comment.
- Extend the fetch() helper (lines 24-29) to take an expected SHA256 and verify it after download with `sha256sum -c` (or compare against a hardcoded digest) BEFORE chmod +x; fail the build (exit non-zero) on mismatch.
- Address the cache-poisoning hole: fetch() currently skips re-download when the file is merely present/executable (`[ -x "$2" ] && return 0`) — change it to also verify the SHA of any pre-existing cached file, so a tampered or stale cached tool is rejected rather than trusted.
- Store the pinned versions + digests in a small manifest (e.g. packaging/tools.lock) that the script reads, so re-pinning is a deliberate, reviewable change.
- Document in the script header that re-pinning is intentional and how to regenerate digests (curl the upstream .sha256 or compute sha256sum).
- **✓ Acceptance:** Every downloaded tool is fetched from a fixed version tag (no 'continuous' remains in the script), and the build aborts with a clear error if any tool's SHA256 does not match the pinned value. Deleting packaging/tools and rebuilding twice produces byte-identical tool binaries. A deliberately corrupted cached tool causes the build to fail rather than run.

#### `P1` Version traceability: VCS-derived version and release provenance
- Initialize a git repository for PMS/ and start tagging releases (vMAJOR.MINOR.PATCH); the project currently has no .git (confirmed), so versions cannot be traced to source.
- In CMakeLists.txt, derive the version at configure time from `git describe --tags --dirty=+` (via execute_process), falling back to project() VERSION 0.1.0 when git/info is unavailable; bake both the version and a short commit hash into PHARMADESK_VERSION (line 122) / a new PHARMADESK_BUILD string.
- Surface the commit hash + dirty flag in the About box and in DesktopIntegration's InstalledVersion comparison (DesktopIntegration.cpp:201-214) so the upgrade-detection logic and About box reflect the actual code running, and a '-dirty' build is visibly non-release.
- Have build-appimage.sh refuse to cut a release AppImage from a dirty/untagged tree (or clearly stamp it as a non-release build) to prevent shipping uncommitted source labeled as a clean version.
- **✓ Acceptance:** About box and logs show e.g. '1.2.0 (abc1234)'; a build from edited-but-uncommitted source shows a '-dirty' suffix and the release script either refuses or visibly marks it. An AppImage's reported version maps to exactly one git commit.

#### `P1` Reproducible AppImage with published, verifiable hash
- Export SOURCE_DATE_EPOCH (from the git commit date) early in build-appimage.sh and pass it through; invoke mksquashfs (line ~184) with `-all-time $SOURCE_DATE_EPOCH -mkfs-time $SOURCE_DATE_EPOCH` so timestamps are normalized.
- Add `-ffile-prefix-map=$here=.` (and -fdebug-prefix-map) to the Release build flags so build-host absolute paths are not embedded via __FILE__.
- Eliminate build-host path leakage from the qmake-wrap / qtplugins symlink farm (the wrapper echoes the absolute $qtplugins path): generate it under a stable relative/canonical location or scrub absolute paths from any generated artifact that lands in the AppDir.
- Make the ICU minimization deterministic (genccode+gcc currently rebuild libicudata fresh each run): pin compiler flags and verify the regenerated lib hashes identically across two runs, or cache the minimized lib keyed by input ICU version.
- After packaging, compute and write PharmaDesk-x86_64.AppImage.sha256 next to the artifact; publish it with each release so the deployed PC's image can be independently verified.
- Add a 'build twice, diff hashes' check (manual or CI) to catch reproducibility regressions.
- **✓ Acceptance:** Two clean builds of the identical committed source on the same host produce byte-identical AppImages (matching SHA256). A .sha256 sidecar is emitted and matches the artifact. No absolute build-host path appears in `strings` of the shipped binary or generated bundle artifacts.

#### `P2` Strict build modes for the money/stock/FEFO core: sanitizers, static analysis, defined build type
- Add option(ENABLE_SANITIZERS OFF); when ON, compile pharmadesk_core + pharmadesk_tests with -fsanitize=address,undefined -fno-sanitize-recover=all and run the 1000+-assertion suite under it — to catch signed-overflow UB, integer overflow, and use-after-free in Money's decimal/string math, CostBlender, and FEFO that -Wall/-Wextra cannot.
- Wire an ASan/UBSan ctest run into CI (or tests/run.sh --sanitize) so the money/stock paths are exercised under the sanitizers regularly, not just optimized.
- Add option(ENABLE_TIDY OFF) setting CMAKE_CXX_CLANG_TIDY on pharmadesk_core only, excluding MOC/AUTOGEN sources (set SKIP_LINTING on generated files) to avoid Qt-generated noise; start with bugprone-* and cppcoreguidelines arithmetic checks.
- Set the standard 'default build type' guard at the top of CMakeLists.txt: if CMAKE_BUILD_TYPE is unset and no multi-config generator, default it to RelWithDebInfo — so the obvious `cmake -S . -B build` dev/test invocation matches the shipped Release codegen (currently dev builds are unoptimized, no NDEBUG; only build-appimage.sh forces Release).
- Treat warnings as errors for first-party translation units only: set a per-target -Werror on pharmadesk_core (not globally, preserving the 'stray MOC/3rd-party warning never blocks the deployment box' rationale).
- **✓ Acceptance:** `cmake -DENABLE_SANITIZERS=ON` builds and the full suite passes clean under ASan+UBSan (zero reports). `cmake -DENABLE_TIDY=ON` runs clang-tidy over core sources without choking on generated MOC. A bare `cmake -S . -B build` yields a RelWithDebInfo build matching release codegen. An introduced warning in a first-party .cpp fails the core build; a third-party/MOC warning does not.

#### `P2` Display-server compatibility on Wayland-default AlmaLinux 10
- Decide and document the target session: either bundle the Qt Wayland platform plugin (add libqwayland-*.so to EXTRA_PLATFORM_PLUGINS at build-appimage.sh:49 and ensure its deps and wayland platforminputcontext are pulled in) for native Wayland, OR explicitly document that the AppImage targets XWayland and confirm XWayland is installed/enabled on the deployed AlmaLinux 10 image.

### Correctness — money/stock/expiry parity with the PHP spec, validation at the data-access trust boundary, and date/timezone consistency

The audit surfaces 68 correctness findings (14 high, 17 medium, 36 low, 1 info) on a medical-retail POS where CLAUDE.md mandates bit-for-bit money/stock/expiry parity with the PHP source. Three systemic root-causes dominate and should drive the clustering rather than treating each finding individually: (1) a single "today" ambiguity — SQLite date('now') is UTC while the C++/PHP domain uses local date — that recurs across FEFO, inventory reporting, receipt numbering, expiry filters, and adjustment numbering (10+ findings), producing internally inconsistent and PHP-divergent behavior for the first ~5 hours of every PKT day; (2) validation and business rules that live only in the Qt UI dialogs instead of the data-access/domain layer, violating CLAUDE.md's "business rules out of the UI" rule and leaving the repositories — the real trust boundary and the layer tests target — wide open to bad data from importers and future callers (10+ findings across batches, medicines, suppliers, settings, sessions); and (3) Money's int64-at-scale-4 representation can silently overflow where PHP's bcmath cannot, and several storage boundaries skip the mandated HALF_UP scale normalization (5+ findings). Two safety-critical stock invariants (express-return restock into quarantined/expired batches; addStock unable to merge duplicate batches) and two regulator-facing money documents (Z-report refund netting; z_report_archive immutability) are P0/P1 because they directly corrupt inventory or misstate cash. The remaining items are parity tightening, observability, and thermal/receipt rendering polish. Priorities reflect production risk: data-integrity/safety and money-misstatement first, broad-rollout parity second, quality third, and faithful-to-PHP-but-worth-noting edge cases last. The plan adds best-practices the raw findings imply but do not state: a single canonical "today/now" clock helper, a shared overflow-checked Money, a centralized validation layer mirroring the PHP controllers, and a PHP-parity golden-test harness so these divergences are locked rather than rediscovered.

#### `P0` Stock-safety invariants and inventory-corruption fixes (highest risk)
- ReturnService::commitReturn(restock=true) (ReturnService.cpp:626-659): read is_quarantined/is_expired and apply the SAME refusal adjudicate() uses (lines 350-369) before bumping current_qty. Extract a single shared restockGuard() helper so the express path and adjudicate() cannot drift.
- ReturnService::voidSale (ReturnService.cpp:766-801): confirm against the PHP void implementation whether per-line restock should be blocked when a batch is now quarantined/expired; if so route restock through the same restockGuard() helper.
- BatchRepository::addStock (BatchRepository.cpp:19): mirror PHP Grn::post() find-or-create — SELECT existing batch by (medicine_id, batch_number, expiry_date); if found UPDATE received/foc/current_qty + refresh cost/MRP and emit GRN_RECEIPT against the existing batch id with correct qty_before/qty_after; else INSERT. Keep inside the single transaction so a re-receive of an already-stocked batch no longer hits the unique index and returns -1.
- CostBlender (CostBlender.cpp:10-12,24-26) + GrnService::post (GrnService.cpp:101): stop returning 0.0000 on invalid input; signal failure the way PHP throws (paidQty>=0, focQty>=0, unitsPerPurchase>=1). Add an explicit unitsPerPurchase>=1 guard in GrnService::post that aborts the post with a user-facing error, and add CHECK("units_per_purchase" >= 1) to the medicines table so a bad CSV/NULL can never INSERT a zero-cost, zero-qty batch.
- GrnService::post (GrnService.cpp:129): change totalBase from 32-bit int to qint64 to match CostBlender's internal width and the batches.current_qty domain.
- Add tests: re-receive same batch+expiry merges (not -1); restock into quarantined/expired batch is refused on both express and void paths; GRN with units_per_purchase=0 is rejected, not silently zeroed.
- **✓ Acceptance:** A second stock-in of an existing (medicine,batch,expiry) updates the existing row and ledger instead of failing; no code path can add returned stock into a quarantined or expired batch; a GRN line with units_per_purchase<1 or negative paid/foc is rejected before any INSERT (schema CHECK + service guard) rather than producing a 0.0000-cost batch; new tests cover all three and pass.

#### `P0` Single canonical clock: eliminate UTC date('now') vs local QDate divergence
- Introduce one app-wide 'today/now' source (e.g. Clock::today() returning QDate::currentDate(), injectable for tests) and a single rule: bind today.toString('yyyy-MM-dd') as a parameter into every expiry/date SQL comparison, OR uniformly use date('now','localtime'). Choose bound-parameter so it is testable and matches PHP server-local CURRENT_DATE.
- Fix every UTC date('now') / mismatched-clock site: BatchRepository.cpp:75 (candidate FEFO) and onHand; SaleService.cpp:253 (batch prefilter) and Fefo::allocate today default (Fefo.h:47) so SQL prefilter and domain re-filter use the SAME local date; InventoryRepository.cpp:40,81,95,124-125,150 (lowStock vs batchList/expiringSoon); AlternativesFinder.cpp:30,34; StockAdjuster.cpp:42 prefix vs count.
- SaleService receipt numbering (SaleService.cpp:31-42,217): make label prefix, the per-day counter, sold_at, and report date filters all agree on one clock — either store sold_at via datetime('now','localtime') or derive prefix/count from date(sold_at) without 'localtime'. Pick one and apply everywhere on the sale path.
- expiringSoon (InventoryRepository.cpp:120-145): add lower bound expiry_date >= today (and/or render days<=0 as EXPIRED) so already-lapsed batches with is_expired=0 stop showing as 'expiring soon' with negative days.
- Add boundary tests pinning a fixed 'today': batch expiring exactly today; a sale committed at simulated 02:00 local asserting receipt prefix matches date(sold_at) used by reports; an integration test that inserts batches via the repo, runs candidateBatchesForSale()/SaleService, and asserts allocate() never drops a SQL-returned row (closes the masked InsufficientStock seam, Fefo.cpp:18).
- **✓ Acceptance:** All expiry/date comparisons across FEFO, inventory, alternatives, sale, and adjustment paths resolve to a single local date identical to PHP CURRENT_DATE; SQL prefilter and domain re-filter never disagree (re-filter is a proven no-op); receipt prefix always matches the date of stored sold_at; boundary tests at local midnight pass and match PHP-equivalent results.

#### `P0` Money fixed-point: overflow safety and HALF_UP scale normalization at storage boundaries
- Money (Money.h:26-28, Money.cpp:58): add overflow detection to operator+, operator-, mul, and fromString (intVal*10000+fracVal) using __builtin_add_overflow/__builtin_mul_overflow; on overflow throw a typed error (or return a sentinel callers must check) so a sale/GRN aborts inside its transaction rather than storing wrapped/negative totals. ### Performance — UI responsiveness, query/index efficiency, and blocking I/O on the single-PC AlmaLinux POS

The performance findings split cleanly into four root causes, none of which threaten data integrity (so nothing here is P0 under the safety-first rubric), but several directly degrade the cashier experience on the most-used screens. (1) Synchronous work on the GUI thread driven by per-keystroke events — live search on the three hottest screens (POS, Medicines, Inventory) and CUPS re-probing in Admin — fires expensive DB queries or blocking QProcess calls on every character, the single highest-ROI fix because it touches the POS terminal latency cashiers feel constantly. (2) Blocking subprocess I/O on the post-sale path (thermal print up to 20s, CUPS probes up to 2s each) freezes the app with no feedback after every sale. (3) SQLite is untuned: no synchronous/cache/temp_store/mmap PRAGMAs, no ANALYZE, a function-wrapped date filter that defeats the sold_at index on the dashboard and every report, and a missing partial index for the 'sellable batch' predicate that FEFO and search hammer. These are pure throughput wins on the exact write-heavy (sale commit) and scan-heavy (reports) paths CLAUDE.md flags as critical — but the date-filter and PRAGMA changes must be validated against the money-exactness and crash-safety guardrails (synchronous=NORMAL+WAL durability vs the MEMORY.md crash-safety note; localtime-offset boundary math must reproduce PHP's date(localtime) semantics bit-for-bit). (4) Unbounded result materialization in analytics and the GRN list, a scaling/parity gap rather than a today problem. I sequence the cheap, high-impact debounce + PRAGMA + index work first (P1, ships before broad rollout), the blocking-print/CUPS off-thread work next (P1/P2 since it affects perceived POS responsiveness), and the report-scaling and pagination work as P2/P3 since the 318-row seed makes them latent. Best practices the raw findings missed: add a lightweight perf-regression guardrail (time the hot queries in a test against a synthetic large dataset, not just the seed), prefer prepared-statement reuse, and ensure WAL checkpointing is bounded so the -wal file doesn't grow unbounded under sustained sale volume.

### Engineering Process & Release Management for PharmaDesk (single-PC Qt6/C++17 medical-retail desktop app, SQLite, CMake, AppImage on AlmaLinux 10, with the PHP POS as the binding specification)

This is a medical-retail system where money, stock, batch, and expiry correctness are patient-safety and regulatory concerns, and the PHP app at ../pos is the contractual spec — so the process must center on PHP-parity golden tests, an auditable trail, and reproducible signed builds rather than feature velocity. The codebase already has the right primitives (a custom test runner with money/salecalc/fefo/costblender/sale/returns cases, a headless smoke test, a screenshot harness, AppImage packaging scripts, and a version stamped in CMake at 0.1.0) but is missing the connective tissue of a professional process: there is NO version control evidence (the repo is "Not a git repo"), NO .github CI, NO clang-tidy/clang-format/static-analysis/sanitizer wiring (CMake only sets -Wall -Wextra, deliberately not -Werror), NO codified golden-fixtures-extracted-from-PHP mechanism (grep found no parity/golden/fixture markers in the money/salecalc/fefo tests, so parity is currently asserted against hand-coded expectations, not against PHP output), and NO formal coverage gate, changelog, release signing, backup/DR runbook, or onboarding doc. Because it is a single-PC AlmaLinux deployment with no server fleet, observability collapses to local structured logging + the HMAC-chained audit_log, and DR collapses to disciplined SQLite backups and a tested restore — these get first-class workstreams. The plan is prioritized P0→P3: P0 establishes the non-negotiable safety net (VCS+review, CI build matrix Qt5/Qt6, the PHP-golden parity harness with a hard coverage gate on money/stock/expiry, and backup/DR), P1 hardens quality and release integrity (static analysis/sanitizers/lint, signed reproducible AppImage + versioning/changelog, structured logging tied to audit), P2 adds compliance/retention and security cadence (DRAP narcotic register retention, audit immutability verification, dependency/security review), and P3 covers docs, runbooks, and onboarding. Acceptance criteria are concrete and CI-enforceable so "done" is observable, not asserted.
